レンタルスタジオサーチアプリ 企画・設計アーカイブ

1. 背景・課題

釣行AIアプリのAnthropic API・AWSアカウントを別アプリでも使い回せるかという相談から、 「このアプリの基盤をほぼそのまま参考にしたレンタルスタジオサーチアプリを作りたい」という 要望に発展した。ダンス・ヨガスタジオという対象を選んだのは、釣行AIアプリと同じ 「実在する場所をGoogle Places APIで発見し、AIが説明・推薦理由を生成する」という パターンがそのまま当てはまるドメインだったため。

想定ユーザー

  • ダンス・ヨガの個人練習者、初心者〜中級者
  • スタジオ選びに時間をかけたくない層

2. スコープ決定: 小さいMVPか、最初から full parity か

計画段階で「釣行AIアプリと同等の機能を最初から実装する」か「小さいMVPから始めて 段階的に拡張する」かを検討した。釣行AIアプリ自体は段階的に機能を積み上げてきた経緯が あることを説明した上で選択を仰いだところ、「釣行AIアプリと同等の機能を最初から」 という方針が明確に選ばれた。理由は、釣行AIアプリという既に検証済みのアーキテクチャ・ コードベースを流用する以上、ゼロから機能を段階検証する必要性が薄いため。 この結果、認証（Cognito+Google）・AI相談・投稿編集・コスト保護レート制限・ reason使い回しキャッシュといった「あると良い」機能も含め、v1から全て実装する 方針で進めることになった。

4. スコアロジックの変遷

当初案（釣行AIアプリの式をそのまま移植）

score = rating_score * 0.4       # Placesのrating(0-5)を0-100に正規化
      + popularity_score * 0.2   # user_ratings_totalを正規化
      + appeal_score * 0.2       # estimate_studio_appeal()のヒューリスティック
      - dist_norm * 0.1          # 基準地点（東京駅）からの距離
      - cost_norm * 0.1          # 常に0（Places APIが料金を返さないため）
この式は「距離」と「費用」が釣行AIアプリの構造をそのまま踏襲しており、 特に距離は「基準地点（東京駅）からの直線距離」という、全国のスタジオを対象にする 本アプリにとってはあまり意味の無い指標だった。費用も常に0固定で、実質機能していなかった。

刷新後（現行）

「釣りと違ってスタジオは天気に左右されず、一度付けたスコアがあまり変わらない」という 指摘をきっかけに、スコア項目を見直した。
項目変更内容理由
距離基準地点からの距離 → 最寄り駅からのアクセス（Places Nearby Search）ユーザーの現在地に依存しない、スタジオ自体の固有の通いやすさを表す指標にするため
収容人数新規追加（capacityCategory）Claudeによる店名・住所からのヒューリスティック推測（設備タグ推測と同方式）。将来のエリア+人数選択機能の土台

5. AWSアーキテクチャの決定

「同じAWSアカウントを使うか、別アカウントか」を検討し、釣行AIアプリと同じAWSアカウント （630956767121）に、完全に独立したCloudFormationスタック（studio-search-app）として構築する 方針を選択した。理由は、口座・請求を分ける必要性が薄く、同一アカウント内でも スタック単位で完全に隔離できるため。ただしCognito User Pool・SSMパラメータパス・ Cloudflare Worker名は、両アプリの運用が互いに影響しないよう明確に分離した。

6. 実装中に発覚した不具合とその対応

Lambda関数名の衝突

初回デプロイ時、多くのLambda関数に釣行AIアプリと同じFunctionName （getRecommendationsHandler等）を固定指定していたため、Lambda関数名の アカウント+リージョン一意制約に反して既存関数と衝突し、 AWS::EarlyValidation::ResourceExistenceCheckでデプロイが失敗した。 全LambdaのFunctionName指定を削除し、CloudFormationに自動採番させる形に 修正して解消した。

フロントエンドの地図が表示されない

デプロイ後、地図ページが表示されない不具合が発生。当初はGoogle Cloud Console側の APIキー制限（HTTPリファラー）が原因と推測したが、実際にブラウザが送信していた リクエストを調査したところ、GitHub SecretsのVITE_GOOGLE_MAPS_KEYに VITE_GOOGLE_MAPS_KEY=という変数名ごと値が登録されていたことが真因だった （.envファイルの行をそのままコピペしたことによる人為的ミス）。値をキー本体のみに 修正して解消した。

7. フロントエンド配信の追加: Cloudflare Workers

当初はAWS（CloudFront）単独で構築したが、釣行AIアプリと同様に「独自ドメイン取得前の 見た目の良い無料URL」としてCloudflare Workersへの並行デプロイを追加した。 Worker名をstudio-search-app（釣行AIアプリはryu-chan-fish）と 明確に別名にし、GitHub Secretsもリポジトリごとに別登録することで、互いのWorkerを 誤って上書きするリスクを排除している。

9. まとめ（2026年7月30日時点、方針転換前）

本プロダクトは「釣行AIアプリのアーキテクチャを、別ドメインに移植する」という形で 立ち上がった。企画段階から「実在データ（Google Places API）とAIによる説明生成を分離し、 AIには存在しないスタジオ・存在しない料金を作らせない」という設計思想を引き継いでおり、 スコアリング刷新（駅距離・収容人数・料金抽出）でもこの原則は一貫して守られている。

10. 大方針転換: AI分析中心アプリ → 4ブランド限定＋空き状況スクレイピング＋イベントおすすめ

これ以降が最新の方針転換の記録。 上記1〜9章は「Google Places APIで全国のスタジオを 自動発見し、AIがスコアを付けておすすめTOP3を出す」という旧構成の企画メモであり、 現在は正確な仕様ではない。本章時点の内容が最新の状態であり、詳細は アプリまるわかりガイド.html／詳細設計.html／ AWS構成・サービス連携.html／ファイル構成・依存関係.htmlを参照。

10.1 転換の背景

運用を続ける中で、「全国のレンタルスタジオをAIが自動発見してスコアを付ける」という 汎用的な設計よりも、実際によく使う特定ブランドの実店舗の空き状況を確実に見せる方が ユーザーにとって実用的ではないか、という指摘があった。特に、口コミ評価・設備・最寄り駅 距離といったスコア項目は「一度計算すればほとんど変化しない」性質のもので、日々AIに 再計算させる意味が薄いという課題も既に7章までの過程で認識されていた。この課題意識を 発展させる形で、対象スタジオをBUZZ／studio worcle／サウンドスタジオNOAH／ スタジオミッションの4ブランドの実店舗のみに絞り込み、AIによるスコアリング機能 そのものを完全に廃止する大方針転換を行った。

10.3 空き状況の取得方法: なぜクラウドの定期バッチではなくローカルスクリプトなのか

新設したbackend/scripts/scrape_availability.pyは、4ブランドそれぞれの公式サイトへ アクセスし、空き状況・部屋の広さ・部屋写真・平面図・設備を取得する。BUZZ・NOAHの一部は 静的HTMLのためBeautifulSoupで足りるが、worcle・ミッションはJavaScriptで空き状況カレンダーを 描画するサイトのためPlaywrightによるブラウザ自動操作が必要になる。さらにミッションは 会員ログインが無いと空き状況が見られない仕様のため、backend/.envに保存した MISSION_LOGIN_EMAIL／MISSION_LOGIN_PASSWORDを使ってPlaywrightから 自動ログインしている。

4ブランドで取得方式がここまでばらつくこと、また会員ログイン情報をクラウド側のSSMではなく ローカルの.envで管理する方針にしたことから、Lambda化・EventBridgeでの 定期実行は行わず、開発者のローカル環境で手動またはタスクスケジューラにより定期実行する という運用に割り切った。この判断により、空き状況の鮮度はローカルスクリプトの実行頻度に 依存する（クラウド側でのSLA保証はない）という制約を許容している。

10.4 イベントおすすめ機能: なぜスコアではなく単純な絞り込みにしたのか

新設した「次のイベント」機能は、発表会・公演等の本番のステージ実寸（横幅・奥行き）と 出演人数を登録しておき、目的（振り入れ／構成）・希望日時・利用時間を指定すると、 条件に合う部屋を提案するというもの。ここでもAIによるスコアリングは行わず、 【広さ条件を満たす】かつ【指定時間帯に空きあり】という2つの条件を機械的に判定するだけの シンプルな絞り込みにした。理由は、4ブランドという限られた対象の中で「間違って予約できない 部屋を勧めてしまう」ことの実害の方が、「AIらしい説明文が付かない」ことより大きいと 判断したため。広さの必要条件は目的によって変え、振り入れ（新しい振付を体に入れる段階）は 1人あたり2.5㎡、構成（隊形確認・仕上げ段階）は1人あたり1.8㎡という目安を設定している （振り入れの方がゆとりを必要とする、という現場の感覚に基づく設定）。

10.5 移行にあたって削除した旧リソース

  • DynamoDB: studio-recommendations テーブル
  • Lambda: generateStudioScoreBatch、adminRunAiBatch（およびgenerate_studio_score.py）
  • API: GET /recommendations、POST /admin/run-ai-batch
  • EventBridge: 毎日AM6:00 JSTのスコア再計算スケジュール
  • フロントエンド: AiBatchButton.tsx、RecommendationCard.tsx、utils/score.ts、useRecommendations.ts
旧構成でスコアリング項目の後追いバックフィルに使っていたbackfill_studio_details.pyは、 既に役目を終えた一回限りのメンテナンススクリプトとしてbackend/scripts/に 残置しているが、今後実行される想定はない（削除するとGit履歴上の経緯が追いにくくなるため、 当面はアーカイブとして残す判断とした）。同様に、4ブランド限定以前に混入したヨガ・ ピラティス系スタジオのクリーンアップにはdelete_yoga_pilates.pyを新規作成し、 一度だけ実行した。

10.6 今後の検討事項

  • 空き状況の取得頻度・失敗時のリトライ方針の明文化（現状は手動実行の裁量に依存）

11. まとめ（方針転換後）

本プロダクトは当初、釣行AIアプリのアーキテクチャをそのまま別ドメインに移植し、 AIによるスコアリングとおすすめTOP3を中心に据えたアプリとして立ち上がったが、 運用を経て「4ブランドの実店舗に対象を絞り、実際の空き状況とイベントの実寸を 突き合わせて絞り込む」という、より実用性を重視したシンプルな設計へ転換した。 「実在データとAI生成を分離し、AIに存在しないものを作らせない」という当初からの 設計思想は転換後も一貫して守られており、AIの役割はAI相談チャットの応答生成のみに 縮小されている。
