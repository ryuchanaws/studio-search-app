ファイル構成・依存関係マップ（レンタルスタジオサーチアプリ）

本書は「どの画面が何をするか」「どのファイルがどのファイルを読んでいるか」を一覧できるようにするための リファレンス。対象を4ブランド（BUZZ／studio worcle／サウンドスタジオNOAH／スタジオミッション）の 実店舗に絞り、AIスコアリング機能を廃止した後の最新構成を反映している。仕様の背景・意思決定理由は AWS構成・サービス連携.html／詳細設計.html／企画・設計アーカイブ.html を参照。

ログイン必須（操作）: お気に入り登録/削除、投稿の作成/編集/削除、AI相談、 イベントの登録/削除/おすすめ検索、現在地から探す（Places APIのコスト保護のため）。

「AI分析を実行」ボタンおよびそれに関連するUI（AiBatchButton.tsx、TOP3表示）は スコアリング機能の廃止にともない削除済み。

3. バックエンド ファイル構成（Lambda・ローカルスクリプト）

3.1 API系（backend/lambda/api/handlers.py 1ファイルに集約）

関数エンドポイント認証読み書きするテーブル/バケット
getStudiosHandlerGET /studios不要Studios（読、対象4ブランドのみフィルタ）
getStudioAvailabilityHandlerGET /studios/{studioId}/availability不要Availability（読。データ無し時はrooms:[]/scrapedAt:nullで200）
postAnalyticsEventHandlerPOST /analytics/event不要AnalyticsEvents（作成）
getEventsHandlerGET /events必須Events（読、userIdでquery）
postEventsHandlerPOST /events必須Events（作成）
deleteEventHandlerDELETE /events/{eventId}必須Events（削除）
getRecommendedStudiosHandlerGET /recommend-studios必須Events（読）, Studios（読）, Availability（読）。広さ・空き状況の両方を満たす部屋のみ抽出
putStudioImageHandlerPUT /studios/{studioId}/image必須Studios（更新）
getPostsHandlerGET /posts不要Posts（読）, Users（読、投稿者の表示名を結合）
postPostsHandlerPOST /posts必須Posts（作成。userIdは_get_user_id(event)で取得しリクエストボディの値は無視）
putPostHandlerPUT /posts/{postId}必須Posts（更新。content/imageUrl/ratingのうち指定されたフィールドのみ更新）
deletePostHandlerDELETE /posts/{postId}必須Posts（削除。postId単一PKで所有者情報がキーに無いため、削除前にget_itemして自分の投稿か明示チェック。他人の投稿は403）
getFavoritesHandlerGET /favorites必須Favorites（読）, Studios（読、結合用）

postPresignUploadHandlerPOST /uploads/presign必須S3 UploadsBucket（署名付きPOSTフォーム発行のみ）
postChatHandlerPOST /chat必須Chats（読み書き）, Usage（1日あたり利用回数のアトミック加算）, Studios（読、実データグラウンディング用）, S3（画像読み取り）, SSM（Claudeキー）
getChatsHandlerGET /chats必須Chats（読、軽量版）
getChatHandlerGET /chats/{chatId}必須Chats（読、全メッセージ）
deleteChatHandlerDELETE /chats/{chatId}必須Chats（削除）
getMyProfileHandlerGET /me必須Users（読）。未登録でも404にせずdisplayName:nullで200を返す

削除済みハンドラー: getRecommendationsHandler（GET /recommendations）は、 RecommendationsTableごと削除されたAIスコアリング機能の廃止にともない削除した。
「認証必須」のエンドポイントは template.yaml の Api リソースに定義した CognitoAuthorizer（Cognito User Pool Authorizer）を通過して初めて呼び出せる。 通過後のイベントには event.requestContext.authorizer.claims.sub にユーザーの一意なID（Cognitoのsub）が入り、_get_user_id(event) ヘルパーがこれを取得する （Favorites/Chats/Eventsテーブルは元々userIdがpartition keyの一部のため、他人になりすまして アクセスすること自体ができない設計。PostsテーブルだけpostId単一PKのため上記の通り明示チェックが必要）。

5. データの流れ（代表的なシナリオ）

5.1 トップ画面での空き状況確認

TopPage.tsx（マウント時）
 → api/client.ts の getStudios() → GET /studios
 → getStudiosHandler（4ブランドのみフィルタして返却）
 → StudioCard一覧を表示（ブランド・エリア・広さで絞り込み可能）
「空き状況を見る」クリック
 → AvailabilityModal.tsx が開き、日付選択
 → api/client.ts の getStudioAvailability(studioId, date) → GET /studios/{studioId}/availability
 → getStudioAvailabilityHandler（AvailabilityTableをget_item。無ければ空データを返す）
 → 部屋ごとの30分刻みタイムテーブルを表示

5.2「次のイベント」登録とおすすめ検索

EventsPage.tsx（イベント登録フォーム）
 → api/client.ts の createEvent() → POST /events
 → postEventsHandler → EventsTableへ保存
EventsPage.tsx（イベント選択＋目的・日付・時間・利用時間を指定して「おすすめを探す」）
 → api/client.ts の getRecommendedStudios() → GET /recommend-studios
 → getRecommendedStudiosHandler
    → EventsTableから対象イベント取得 → 目的別の必要面積(㎡/人)を算出
    → StudiosTable全件scanし、広さ条件を満たすroomを抽出
    → AvailabilityTableで指定日時のslotsを確認し、空きのあるroomのみ残す
 → 条件を満たす{studio, room}の一覧をEventsPageに表示（スコア付けはしない）

5.3 空き状況データの収集（ローカル、クラウドを介さない）

開発者PCで python backend/scripts/scrape_availability.py を実行（手動 or タスクスケジューラ）
 → 4ブランドそれぞれの公式サイトへアクセス
    ・BUZZ/NOAH: BeautifulSoupで静的HTMLを解析（NOAHは一部Playwright併用）
    ・worcle/ミッション: Playwrightでブラウザを自動操作しJS描画後のDOMを取得
      （ミッションはbackend/.envのMISSION_LOGIN_EMAIL/PASSWORDで事前ログイン）
 → 空き状況（30分刻み）・広さ・写真・平面図・設備を取得
 → ローカルのAWS認証情報でStudiosTable（部屋マスタ）・AvailabilityTableへ直接書き込み
   （Lambda/API Gatewayを経由しない）

5.4 チャットで写真つきの質問をしたとき

ChatInput.tsx（写真選択 + 送信）
 → useChat.ts の send()
   → api/client.ts の getPresignedUploadUrl() → POST /uploads/presign
   → api/client.ts の uploadImageToS3()（S3へ直接POST、バックエンドを経由しない）
   → api/client.ts の sendChatMessage() → POST /chat
 → postChatHandler（handlers.py）
   → S3から画像バイトを取得 → Claudeへマルチモーダル入力として送信
   → Chatsテーブルへ保存 → 応答を同期的に返却

5.5「初心者でも通えるスタジオある？」とAI相談で聞いたとき

ChatInput.tsx（現在地共有トグルON + 送信）
 → useChat.ts の send()（lat/lngを含めてsendChatMessage呼び出し）
 → POST /chat
 → postChatHandler（handlers.py）
   → _build_studios_context(lat, lng) がStudiosをscan→
     現在地からの距離（haversine）で近い順にソート→上位N件をテキスト化
     （旧来のスコア・reasonは含まない。Studiosの実データのみ）
   → _generate_chat_reply() のsystem_instructionに上記テキストを埋め込む
     （「データに無いスタジオは作り出さない」という指示も併記）
   → Claudeが実データの中から回答を組み立てる

6. 使用サービスとコストの目安

釣行AIアプリと同じAWSアカウント上で運用しているため、AWS側の各サービスは既存分と合算で 無料枠・低ボリューム内に収まる想定。正確な最新料金は各サービスの公式ページで確認すること （料金体系は変更されうるため、あくまで目安）。AIスコアリング機能の廃止にともない、 Claude API・Google Places APIの呼び出し頻度は旧構成よりさらに低くなっている （AI相談チャットと「現在地から探す」時のみ）。
サービス課金対象個人利用規模での目安

AWS側は CostBudget（AWS Budgets、月$10・80%/100%到達時にメール通知）で自動監視している。 Google Cloud側（Places/Maps）とAnthropic側（Claude）はAWS Budgetsの対象外のため、 それぞれのコンソールで別途予算アラート・spend limitを手動設定する必要がある （README.md参照）。
